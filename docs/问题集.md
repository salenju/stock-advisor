## 一、CSV 导入

### Q1 「导入 CSV」有模板文件吗？在哪里下载？

有。

| 项目 | 说明 |
| --- | --- |
| 入口 | 顶部工具栏「导入CSV」→ 弹窗内文件选择框下方的「下载模板」按钮 |
| 文件名 | `stock-advisor-import-template.csv`（UTF-8 带 BOM，Excel 直接打开不乱码） |
| 生成方式 | 前端生成，不是静态文件：`web/src/core/csv.js` → `buildImportTemplateCsv()` |
| 内容 | 表头 + 4 类操作示例行（买入 / 卖出 / 分红 / 送转），名称统一标为「示例·请替换或删除本行」，代码用 `000000` / `999999` |
| 注意 | 示例行是真实数据行，**导入前请替换成自己的记录或删除示例行**，否则会新建一只「示例」持仓 |

模板表头（12 列，与解析规则一一对应）：

```
序号,股票/基金名称,代码,地区,类型,操作,日期,数量,价格,手续费,金额,比例
```

| 列 | 是否必需 | 取值 / 说明 |
| --- | --- | --- |
| 序号 | 否 | 仅便于核对，不参与计算 |
| 股票/基金名称 | 否* | 别名：`名称`。*自动新建持仓时用于命名，缺省用代码 |
| 代码 | **是** | 原样匹配持仓代码；匹配不到再按数字归一（见 Q2） |
| 地区 | 否* | 建议 `hk` / `us` / `sh` / `sz`（与下拉框一致）；也兼容「港股/美股/A股/沪/深」中文标签。*自动新建持仓时必需 |
| 类型 | 否* | `股票` / `股票型基金` / `债券型基金` / `货币型基金` / `ETF`。*自动新建持仓时必需 |
| 操作 | **是** | 买入（买）、卖出（卖）、分红（红利/派息）、送转（送股/转增/拆） |
| 日期 | **是** | 别名：`交易日期` / `买入日期` / `卖出日期`；支持 `2026-01-05`、`2026/1/5`、`2026.1.5`、ISO 时间戳，统一归一为 `YYYY-MM-DD` |
| 数量 | 买入/卖出必需 | 别名：`买入数量` / `卖出数量` |
| 价格 | 买入/卖出必需 | 别名：`买入价` / `卖出价` |
| 手续费 | 否 | 别名：`佣金` / `费用`；留空按 0 |
| 金额 | 分红必需 | 别名：`分红金额`；分红总额（本地币种） |
| 比例 | 送转必需 | 别名：`送转比例` / `送股比例` / `拆分比例`；必须 > 0 且 ≠ 1（10 送 10 填 2） |

缺少 `代码` / `操作` / `日期` 三列会直接报错，不会写入任何数据。

### Q2 导入的数据是「往后追加」还是「覆盖已有数据」？

**结论：只追加，不覆盖。** 导入不会清空、不会删除、不会改写任何已有持仓或已有明细。

流水线（`web/src/services/dataSource.js` → `importCsv`）：

```
读取本机现有持仓列表
  → importCsvText(列表, CSV)  // 原地追加明细、必要时新建持仓
  → persistLocal('CSV 导入')  // 整包写回 IndexedDB（内容 = 旧数据 + 新增明细）
```

写盘时 `localStore.saveHoldings` 会先调用 `backupIfChanged` 留一份版本快照（最多 30 份，可在「数据」面板回滚）；GitHub 模式下只有交易数据指纹（`dataSignature`）变化才会触发云端推送，导入属于交易数据变化，会推送。

#### 场景 A：导入相同股票（代码能匹配上现有持仓）

| 动作 | 结果 |
| --- | --- |
| 匹配方式 | 先按 `代码` 精确匹配；匹配不到再按数字归一兜底（`01810` ↔ `1810`、`hk00700` ↔ `700`） |
| 新明细 | 逐条调用 `applyTransaction`，追加到该持仓的 `purchases` / `sells` / `dividends` / `splits` 数组**末尾** |
| 已存在明细 | 判定为重复 → 计入「已存在·忽略」，不重复写入 |
| 原有明细 | 一条不动，历史卖出记录里已落盘的成本/盈亏也是账本事实，不会被重算 |
| 持仓级字段 | `name` / `region` / `type` / `strategy` / `costMethod` 等不被 CSV 修改 |
| 重复导入同一份 CSV | 第一次新增 N 条，第二次全部「已存在·忽略」，明细总数不变（幂等） |

幂等判定键（`web/src/core/import-csv-core.js` → `existingKey`）：

| 操作 | 唯一键 |
| --- | --- |
| 买入 / 卖出 | (日期, 数量, 价格) |
| 分红 | (日期, 金额) |
| 送转 | (日期, 比例) |

#### 场景 B：导入不同股票（代码匹配不到现有持仓）

| 勾选状态 | 结果 |
| --- | --- |
| 未勾选「匹配不到现有持仓时自动新建持仓」（默认） | 这些记录只进入结果的 `missing` 列表，**不写入任何数据**，原有持仓完全不变（有单测保证原数据 JSON 不变） |
| 已勾选 | 用 CSV 的名称 / 代码 / 地区 / 类型新建一条持仓（`status=持有`，成本法取弹窗默认），再把该代码的记录追加进去；其它持仓不受影响 |

#### 导入结果字段

| 字段 | 含义 |
| --- | --- |
| `added` | 实际新增的明细条数 |
| `skipped` | 判定为已存在、被忽略的条数 |
| `created` / `createdCodes` | 自动新建的持仓数量 / 列表 |
| `missing` | 匹配不到持仓、未写入的记录（可勾选自动新建后重试） |
| `errors` | 账本校验失败（如卖出超过持仓）的记录及原因 |
| `total` | CSV 中通过格式校验的记录总数 |

### Q3 导入有哪些容易踩的坑？

1. **幂等键不含手续费**：只改了手续费的行会被判为重复而忽略；同一股票「同日期+同数量+同价格」的两笔真实成交也会被判为重复（可先改日期或事后手工补录）。
2. **卖出仍走账本校验**：卖出数量超过当前持仓 → 进 `errors`，该条不写入，其余记录照常导入。
3. **买入会把状态翻回「持有」**：给已「全部卖出」的持仓导入买入记录，状态会被重置为「持有」。
4. **送转比例不能为 1**：`比例=1` 会被拒绝（视为无效送转）。
5. **导出的 CSV 不能直接回导分红**：`导出交易明细 CSV` 的列是 `… 手续费,成本价,盈亏,收益率%`，**没有「金额」列**，分红行导出后再次导入会被跳过（数量/价格为空）。回导前需补上 `金额` 列，或分红直接在页面补录。
6. **代码归一存在误匹配风险**：不同市场但数字相同的代码（如 A 股 `000700` 与港股 `00700`）在数字归一后会命中同一条持仓；建议 CSV 里写带前缀或完整格式的代码，且持仓代码格式保持统一。
7. **模板示例行是真实数据**：下载模板后不删示例行直接导入，会新增一只「示例」持仓（未勾选自动新建时则进 `missing`，无害）。

## 二、成本核算（FIFO / LIFO）

### Q4 FIFO 和 LIFO 有什么区别？

**结论：两者只差一件事——卖出时先扣哪一批买入。** FIFO 扣最早的批次（先买先卖），LIFO 扣最新的批次（后买先卖）。买入记录一条都不会被改写，变的只是「这笔卖出算多少成本」，进而影响单笔已实现盈亏和剩余持仓均价。

| 对比项 | FIFO（先进先出） | LIFO（后进先出） |
| --- | --- | --- |
| 扣减顺序 | 买入日期**最早**的剩余批次优先 | 买入日期**最新**的剩余批次优先 |
| 单笔卖出成本 | 取老批次的单位成本 | 取新批次的单位成本 |
| 价格上涨时（低买高买） | 卖出成本低 → 单笔利润高 | 卖出成本高 → 单笔利润低 |
| 剩余持仓均价 | 偏高（留下的是贵批次） | 偏低（留下的是便宜批次） |
| 已实现 / 未实现分布 | 已实现偏多、未实现偏少 | 已实现偏少、未实现偏多 |
| 总盈亏（已实现+未实现） | **完全相同** | **完全相同** |
| 直觉与实务 | 「先买的先卖」，A 股个人记账常用 | 偏税务/报表口径，部分市场（如 IFRS）不允许 |
| 数据结构类比 | 队列 Queue（先进先出） | 栈 Stack（后进先出） |

> 第 6 行是最容易被忽略的结论：成本法不改变你赚了多少钱，只改变「利润记在哪一年、已实现还是浮盈」。真正会被影响的是**当期已实现收益、胜率、年度收益归因**。

#### 示例 1：一批买入 + 一次部分卖出（不计手续费）

| 日期 | 操作 | 数量 | 价格 | 金额 |
| --- | --- | --- | --- | --- |
| 2026-03-02 | 买入 A | 100 | 10 | 1,000 |
| 2026-04-02 | 买入 A | 100 | 20 | 2,000 |
| 2026-05-04 | 卖出 A | 100 | 30 | 3,000 |

卖出这 100 股该算谁的成本？

| 口径 | 扣减批次 | 卖出成本价 | 本笔已实现盈亏 | 剩余 100 股成本 | 剩余均价 |
| --- | --- | --- | --- | --- | --- |
| FIFO | 3 月那批（@10） | 10 | (30−10)×100 = **2,000** | 2,000 | **20** |
| LIFO | 4 月那批（@20） | 20 | (30−20)×100 = **1,000** | 1,000 | **10** |

假设现价 25 元，把两边加起来看总额：

| 口径 | 已实现 | 未实现 (25−均价)×100 | 合计 |
| --- | --- | --- | --- |
| FIFO | 2,000 | 500 | **2,500** |
| LIFO | 1,000 | 1,500 | **2,500** |

同样的三笔交易，FIFO 让「已实现利润」多 1,000、浮盈少 1,000；总额一分不差。

#### 示例 2：一次卖出跨两个批次

2026-05-04 改为卖出 **150** 股 @30：

| 口径 | 扣减明细 | 卖出成本 | 成本价 | 本笔盈亏 | 剩余 50 股成本 | 剩余均价 |
| --- | --- | --- | --- | --- | --- | --- |
| FIFO | 100×10 + 50×20 | 2,000 | 13.33 | 4,500−2,000 = **2,500** | 1,000 | 20 |
| LIFO | 100×20 + 50×10 | 2,500 | 16.67 | 4,500−2,500 = **2,000** | 500 | 10 |

卖出数量超过总持仓时，本项目直接报错、不落盘（`derive.js` → `consumeCost` 返回 `insufficient`）。

#### 示例 3：按本项目的口径带上手续费

本工具的计算口径（`web/src/core/derive.js`）：

```
买入单位成本 = 买入价 + 手续费 / 数量     // 手续费摊入成本，见 unitCostOf()
单笔卖出盈亏 = (卖出价 − 成本价) × 数量 − 卖出手续费
```

沿用示例 1 的两笔买入，各加 5 元手续费：

| 批次 | 买入 | 单位成本 |
| --- | --- | --- |
| 第 1 批 | 100 @10，费 5 | 10 + 5/100 = **10.05** |
| 第 2 批 | 100 @20，费 5 | 20 + 5/100 = **20.05** |

卖出 100 @30，卖出手续费 5：

| 口径 | 成本价 | 盈亏 = (30−成本价)×100 − 5 |
| --- | --- | --- |
| FIFO | 10.05 | **1,990** |
| LIFO | 20.05 | **990** |

#### 示例 4：送转之后（顺序不变，只改单位成本）

第 1 批在 2026-04-20 遇到「10 送 10」（比例 2）：

| 批次 | 送转前 | 送转后 |
| --- | --- | --- |
| 第 1 批 | 100 股 / 单位成本 10.05 | **200 股 / 单位成本 5.025**（成本金额 1,005 不变） |
| 第 2 批 | 100 股 / 单位成本 20.05 | 不变（送转日之前没有买入） |

之后再卖 100 股 @30：

| 口径 | 扣减批次 | 成本价 | 盈亏 |
| --- | --- | --- | --- |
| FIFO | 第 1 批（送转后） | 5.025 | (30−5.025)×100−5 = **2,492.5** |
| LIFO | 第 2 批 | 20.05 | **990** |

送转只摊薄单位成本、改变份额，**不改变批次先后顺序**（仍按 `buyTime` 排序）。

### Q5 本项目的成本法怎么设、默认是哪个？

| 项目 | 说明 |
| --- | --- |
| 可选值 | `FIFO` 先进先出 / `LIFO` 后进先出 / `WAC` 移动加权平均 |
| 默认值 | **FIFO**（`derive.js` → `normalizeCostMethod` 兜底 `'FIFO'`；`constants/options.js` 注释也写「FIFO 为默认」） |
| 作用范围 | 逐只持仓独立设置，字段 `costMethod`；改它不会动买入记录 |
| 计算入口 | 所有口径统一走 `web/src/core/derive.js` → `computePositions()`（页面、CSV 导入、策略、统计同源） |
| 卖出量校验 | 超出剩余数量 → 该笔报错不写入 |

⚠️ **切换成本法不会自动改写历史卖出记录**：`sells[].costPrice` / `profit` 在录入那一刻已落盘，切换后默认原样沿用（`computePositions` 中 `source='stored'` 分支）。要让历史的卖出按新成本法重算，必须显式执行「按当前成本法重算历史成本」（`POST /api/holdings/:id/recompute`），该操作会改写历史，建议先备份。

📌 文档口径已同步：`盈亏计算规则.md` §2.2 已于 2026-11-07 改为「`FIFO`（默认，券商口径）」，与代码（`derive.js` L39-48）一致。

### Q6 我该选 FIFO 还是 LIFO？

| 你的诉求 | 建议 |
| --- | --- |
| 「先买的先卖掉」的直觉、和券商/记账软件对得上 | **FIFO**（项目默认） |
| 想让已实现利润尽量低（价格一路上涨时压当期收益） | LIFO（注意部分市场会计准则不允许） |
| 不想纠结批次、只想看一个平滑的均价 | **WAC 移动加权平均** |
| 同一只标的反复加减仓、批次很碎 | WAC；或保持 FIFO 但别频繁切换 |

一句话：**成本法只影响利润的时间分布与指标口径，不影响总盈亏**；选定后尽量不来回切，切换后记得决定是否重算历史。

### Q7 切到 FIFO 后「卖出收益」变少了，那持仓成本是不是也相应变低了？

**结论：是，而且两边减少的金额完全相同。** 成本法只决定「卖掉的是哪一批筹码」，把利润在「已实现」和「未实现」之间挪位置——**总盈亏一分不差**。

#### 实测案例（小米，2026-11-07 实盘数据）

买入 5 笔、合计 2,800 股 / 82,568 元（无手续费）：

| 买入日 | 数量 | 价格 | 成本 |
| --- | --- | --- | --- |
| 2026-05-05 | 1,400 | 30.70 | 42,980 |
| 2026-05-11 | 400 | 31.72 | 12,688 |
| 2026-07-03 | 200 | 23.90 | 4,780 |
| 2026-07-21 | 400 | 27.84 | 11,136 |
| 2026-09-07 | 400 | 27.46 | 10,984 |

2026-11-06 卖出 1,600 股 @30.88（回款 49,408），现价 30.38。这笔卖出在旧口径（LIFO）下的成本是 45,728（= 10,984 + 11,136 + 4,780 + 12,688 + 200×30.70）。

| 项目 | LIFO（旧） | FIFO（新） | 差额 |
| --- | --- | --- | --- |
| 卖出 1,600 股的成本 | 45,728 | 49,324 | +3,596 |
| 已实现收益 | +3,680（+8.05%） | **+84（+0.17%）** | **−3,596** |
| 剩余 1,200 股成本 | 36,840 | **33,244** | **−3,596** |
| 剩余均价 | 30.70 | **27.70** | −3.00 |
| 剩余市值（30.38） | 36,456 | 36,456 | 0 |
| 未实现收益 | **−384（−1.04%）** | **+3,212（+9.66%）** | **+3,596** |
| 已实现 + 未实现 | +3,296 | +3,296 | **0** |

验算：卖出回款 49,408 + 剩余市值 36,456 − 总买入成本 82,568 = **3,296**，两种口径完全一致。

#### 为什么必然相等

```
总盈亏 = 卖出回款 + 期末市值 − 总买入成本（含费）
```

这三个数都不受成本法影响；成本法只重新分配「卖出成本」。所以：

```
卖出成本 +3,596  ⇒  已实现 −3,596
剩余成本 −3,596  ⇒  未实现 +3,596
```

#### 三个容易误读的点

1. **持仓收益率从 −1.04% 变成 +9.66%**：分母（持仓成本）变小导致的口径变化，不是真的多赚了 3,596。
2. **回本价从 30.70 降到 27.70**：手里剩下的批次变便宜了（先卖掉的是最早那批 30.70）。
3. **税务视角**：本例 FIFO 已实现利润更低（先卖的是较贵的早期批次）；价格单边上涨时结论会反过来（FIFO 先卖便宜筹码 → 已实现利润更高）。

### Q8 券商按 FIFO 记账，怎么把老数据一次性切过去并重算？

**结论：新版首次启动会自动做一次性迁移（切 FIFO + 按 FIFO 重算历史卖出成本）；「数据」面板里也保留手动入口。**

| 项目 | 说明 |
| --- | --- |
| 触发时机 | `web/src/store/localStore.js` → `loadHoldings()`：`meta.fifoMigrated` 不存在时执行一次 |
| 只执行一次 | 迁移成功后写入 `meta.fifoMigrated = true`；之后即使手动切回 LIFO 也不会被改回来（实测） |
| 迁移逻辑 | `web/src/core/fifo-migration.js` → `convertAllToFifo()`：`costMethod='FIFO'` + `recomputeSells()` 按 FIFO 重写 `sells[].costPrice/profit/returnRate` + `syncFromPurchases()` 闭合汇总字段 |
| 迁移前备份 | 落盘走 `saveHoldings()`，写盘前自动留一份版本快照，面板里回滚即可恢复（实测备份原因：`成本法统一为 FIFO（券商口径）`） |
| 云同步模式 | 迁移后自动 `scheduleAutoPush` 推一次，避免另一台设备拉取时把 LIFO 覆盖回来 |
| 手动入口 | 「🗄 数据 → 成本核算方法 → 全部改为先买先卖（FIFO）」；单只持仓：卡片「✎ → 成本法」 |
| 只切不算的后果 | 剩余批次成本合计 ≠ 持仓成本 → 展开持仓会出现黄色提示条，并提供「按当前成本法重算」按钮 |

本次实测（小米）迁移结果：卖出成本价 28.58 → **30.8275**，已实现收益 3,680 → **84**，剩余成本 36,840 → **33,244**，卡片成本法徽章 `LIFO → FIFO`。

⚠️ 迁移会**改写历史卖出盈亏**（本例 3,680 → 84）。如果历史卖出成本是券商确认过、想原样保留的账本事实，可在「数据」面板直接回滚到迁移前的快照，并把该持仓手动改回 LIFO。
